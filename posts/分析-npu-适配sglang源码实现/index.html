NPU（Ascend）适配全面分析

SGLang 的 NPU 适配是一个 分层替换 + 插件注册 的架构模式，没有对原有 GPU 代码进行大规模修改，而是通过 策略模式 + 装饰器注册 + 条件导入 在关键路径上插入 NPU 专属实现。下面从 5 个层次详细拆解。

一、设备发现与后端初始化（Entry Point）

文件： utils/common.py:149-158

def is_npu() -> bool:
    if not hasattr(torch, "npu"):
        return False
    if not torch.npu.is_available():
        raise RuntimeError("torch_npu detected, but NPU device is not available.")
    return True
  • is_npu() 是全局设备检测函数，通过检测 torch.npu 属性和 torch.npu.is_available() 来判断
  • 在模块加载时以 _is_npu = is_npu() 形式缓存结果，遍布 30+ 个文件

初始化链：

  1. server_args.py:1112-1116 — _handle_npu_backends() 调用 set_default_server_args(self)，强制设置 attention_backend="ascend"、禁用 CustomAllReduce、根据 NPU 型号设置 page_size/chunked_prefill_size/cuda_graph_max_bs 等默认参数
  2. model_runner.py:206-209 — 在模块加载时调用 init_npu_backend()，该函数只执行一次：
    • 导入 sgl_kernel_npu（NPU 自定义算子库）
    • 导入 torch_npu 及 transfer_to_npu（将 torch.cuda 接口重映射到 torch.npu）
    • 关键技巧：torch.cuda.is_available = lambda: False — 因为 transfer_to_npu 会把 torch.cuda.is_available mock 成 True，但 sglang 很多路径靠这个判断是 CUDA 还是非 CUDA，所以强制恢复

二、注意力机制适配（最核心部分）

NPU 适配最复杂的是注意力层，分为 AttentionBackend（运行时调度）和 DeepSeek MLA forward 方法（模型前向）两个层面。

2.1 AttentionBackend 注册机制

文件： layers/attention/attention_registry.py:79-85

@register_attention_backend("ascend")
def create_ascend_backend(runner):
    from sglang.srt.hardware_backend.npu.attention.ascend_backend import AscendAttnBackend
    return AscendAttnBackend(runner)

通过装饰器注册 "ascend" 字符串到 AscendAttnBackend 类的映射。当 server_args 中 attention_backend="ascend" 时，框架自动使用这个后端。

2.2 AscendAttnBackend 结构（~2100 行）

继承自 AttentionBackend（抽象基类），实现了以下核心方法：

  2. 传统路径 → 使用 _npu_flash_attention_qlens（extend）和 _npu_paged_attention（decode）

2.3 AttnForwardMethod 调度（DeepSeek MLA 模型特有）

对于 DeepSeek V2/V3 这类使用 MLA 的模型，不是通过 AttentionBackend 调用，而是在模型的 dispatch_attn_forward_method() 中决定。

文件： deepseek_common/attention_backend_handler.py:38-53

def handle_attention_ascend(attn, forward_batch):
    # extend 阶段 → MHA_NPU（或 DSA_NPU 如果有 indexer）
    # decode 阶段 → MLA_NPU（或 DSA_NPU）
    if forward_batch.forward_mode.is_extend():

三、KV Cache 与内存管理

3.1 Token-to-KV Pool

文件： npu/memory_pool_npu.py

  • NPUMHATokenToKVPool（继承 MHATokenToKVPool）：
    • 连续内存分配：[2, layer_num, num_pages+1, page_size, head_num, head_dim]，+1 的 slot 0 用于 dummy padding
    • FIA 模式下 KV buffer 变为 list of per-layer tensors，方便 scatter_nd_update
    • set_kv_buffer() 使用 torch_npu.npu_scatter_nd_update_() 或 torch_npu._npu_reshape_and_cache()（FIA vs 传统）
  • NPUMLATokenToKVPool（继承 MLATokenToKVPool 的父类）：
    • K_buffer 存 kv_lora_rank，V_buffer 存 qk_rope_head_dim，完全分离
    • 均使用 npu_scatter_nd_update_ 写入

3.2 Paged 内存分配器

文件： npu/allocator_npu.py

NPUPagedTokenToKVPoolAllocator 继承 PagedTokenToKVPoolAllocator：

  • alloc_extend() — 小 batch（<200 pages）使用 sgl_kernel_npu.mem_cache.allocator.alloc_extend_kernel（NPU 专属 kernel），大 batch 走原始的 alloc_extend_naive
  • alloc_decode() — 与 CUDA 版本逻辑相同但适配了 NPU 的数据类型

核心策略：

  1. 设备感知 — is_npu() 作为全局开关，在模块加载时缓存
  2. 条件导入 — if _is_npu: from ..._npu import ... 替换关键函数
  3. 继承覆盖 — NPU 类继承 GPU 基类，只重写需要差异的方法（如 NPUMHATokenToKVPool）
  4. 装饰器注册 — @register_attention_backend("ascend") 将 NPU 后端插入框架的 AttentionBackend 工厂
  5. 策略注册 — AttentionBackendRegistry.register("ascend", handle_attention_ascend) 调度 DeepSeek 的 MLA 前向策略
  6. 透明算子 — 通过 sgl_kernel_npu（自定义 NPU 算子库）暴露与 sgl_kernel 相同接口的算子，模型层基本无感知

KV Cache 与内存管理部分需要适配的根本原因

这是 NPU 适配中非常关键的问题。NPU 需要独立适配 KV Cache 和内存管理，核心原因在于 Ascend NPU 的硬件架构和内存访问模式与 NVIDIA GPU 有本质差异。让我从具体的代码差异来拆解原因。

1. 内存布局：GPU 是 [num_pages, page_size, head_num, head_dim]，NPU 是 [2, layer_num, num_pages+1, page_size, head_num, head_dim]

看 memory_pool_npu.py:55-68：

# GPU 版本（基类 MHATokenToKVPool）：
self.kv_buffer = torch.zeros((num_pages, page_size, head_num, head_dim))  # 扁平排列

# NPU 版本（NPUMHATokenToKVPool）：
self.kv_buffer = torch.zeros((
    2,                          # 第0维: k=0, v=1
    self.layer_num,             # 第1维: 按层排列
    self.size // self.page_size + 1,  # 第2维: page数(+1是dummy slot 0)
    self.page_size,             # 第3维: page内token数
    self.head_num,              # 第4维: head数
    self.head_dim,              # 第5维: head维度
))

为什么？ Ascend 的 npu_scatter_nd_update_ 和 _npu_reshape_and_cache 算子要求 KV cache 是 连续的 5D/6D 张量，才能用硬件加速的 DMA 写入。GPU 的 KV cache 是逐 page 间接索引写入，而 NPU 需要一次 scatter 操作写入整个块，连续内存布局对 Ascend 的传输后端效率至关重要。

2. set_kv_buffer：GPU 用 index_copy_，NPU 用 scatter_nd_update_

看看写入方式的根本差异：

GPU（MHATokenToKVPool 基类）：

# 使用 index_copy_ 按 slot 逐一写入
self.k_buffer[layer_id - self.start_layer].index_copy_(0, loc, cache_k)

NPU（NPUMHATokenToKVPool）：

# FIA 模式：用 scatter_nd_update_，一次写入整个 page block
torch_npu.npu_scatter_nd_update_(
    k_buffer_layer,                      # [num_pages+1, 1, head_num, head_dim]
    loc.view(-1, 1),                     # 位置索引
    cache_k.view(-1, 1, head_num, head_dim),  # 要写入的数据
)

# 非 FIA 模式：用 _npu_reshape_and_cache，这是 Ascend 专属
torch_npu._npu_reshape_and_cache(
    key=cache_k, value=cache_v,
    key_cache=self.k_buffer[...].view(-1, page_size, head_num, head_dim),
    value_cache=self.v_buffer[...].view(-1, page_size, head_num, head_dim),
    slot_indices=loc,
)

npu_scatter_nd_update_ 是 Ascend CANN 的专属算子，GPU 没有对应物。它允许根据坐标索引批量更新多维张量的指定位置。而 _npu_reshape_and_cache 是 Ascend 为 KV cache 场景专门优化的算子，会处理 page 边界对齐和 cache line 填充。

3. 为什么 alloc_extend 也需要适配

看 allocator_npu.py:28-94：

class NPUPagedTokenToKVPoolAllocator(PagedTokenToKVPoolAllocator):
    def __init__(self, ...):
        super().__init__(...)
        self.roundup = page_size - 1  # 新增：用于 page 对齐计算

    def alloc_extend(self, ...):
        if num_new_pages_item < 200:
            # 小 batch 走 NPU 专属的 kernel（sgl_kernel_npu）
            from sgl_kernel_npu.mem_cache.allocator import alloc_extend_kernel
            alloc_extend_kernel[(bs,)](...)
        else:
            # 大 batch 走原来的 CPU naive 逻辑
            out_indices = torch.empty(..., dtype=torch.int32)  # NPU 用 int32
            alloc_extend_naive(...)

GPU 版本的差异点：

  • NPU 的 alloc_extend 增加了小 batch 的 kernel 加速路径（sgl_kernel_npu.mem_cache.allocator.alloc_extend_kernel），这是一个在 Ascend NPU 上编译的 Triton/CANN kernel
  • NPU 在 alloc_decode 中 out_indices 的数据类型与 GPU 版本不同（NPU 用 int32）
  • num_new_pages 的计算公式中新增了 self.roundup 对齐，因为 Ascend 的 page 分配需要 FRACTAL_NZ 格式对齐

4. MLA 模式下 KV 分离存储

NPU 对 MLA（Multi-head Latent Attention）的 KV cache 布局也不同：

class NPUMLATokenToKVPool(MLATokenToKVPool):
    # k_buffer: 存 kv_lora_rank（压缩后的 key+value)
    self.k_buffer = zeros([layer_num, num_pages+1, page_size, 1, kv_lora_rank])
    # v_buffer: 存 qk_rope_head_dim（旋转位置编码）
    self.v_buffer = zeros([layer_num, num_pages+1, page_size, 1, qk_rope_head_dim])

GPU 的 MLA KV cache 通常是 扁平连续存储 kv_lora_rank + qk_rope_head_dim，或者通过 FlashMLA 的专用接口管理。而 NPU 将两者物理分离到独立的 buffer，因为 Ascend 的 sparse flash attention 需要分别传入 key（nope 部分）和 key_rope（rope 部分），不能合并。

5. 内存对齐要求：FRACTAL_NZ

utils.py:110-129 中的 _is_nz_aligned：

def _is_nz_aligned(tensor: torch.Tensor) -> bool:
    k, n = tensor.shape[-2], tensor.shape[-1]
    if tensor.dtype in (torch.bfloat16, torch.float16):
        return k % 16 == 0 and n % 16 == 0
    if tensor.dtype == torch.int8:
        return k % 16 == 0 and n % 32 == 0

Ascend NPU 的矩阵乘法单元（Cube Unit）对 FRACTAL_NZ 格式有极致优化，需要最后两维对齐到 16 的倍数。如果 KV cache 的 page_size * head_dim 不满足对齐条件，性能会大幅下降。因此 NPU 的分配器必须保证 page 大小和对齐要求。

总结：适配的驱动因素

适配点GPU (CUDA)NPU (Ascend)适配原因
内存布局[pages, page_size, H, D] 扁平[2, layers, pages+1, page_size, H, D] 连续 6DAscend 的 scatter/reshape 算子要求连续多维布局；slot 0 是 padding 要求
KV 写入index_copy_ 逐位置npu_scatter_nd_update_ / _npu_reshape_and_cacheNPU 没有 index_copy_ 的高效硬件支持，用 scatter_nd 一次多位置写入
Page 分配alloc_extend_naive小 batch 用 NPU kernel + roundup 对齐Ascend 需要 FRACTAL_NZ 格式对齐 + 硬件 page 分配器
MLA 存储kv 合并存储k_buffer(v_nope) / v_buffer(k_rope) 物理分离Ascend sparse flash attention 接口要求分别传入 nope 和 rope
格式约束无特殊要求最后两维需 %16==0 (NZ 对齐)Ascend 矩阵乘法单元对 NZ 格式有硬件依赖
内存池无额外层+1 slot 做 padding避免 NPU 上的 page 越界导致硬件异常

简单说：NPU 的 CANN 运行时提供的算子接口（scatter_nd_update、reshape_and_cache、flash_attention 等）与 CUDA 的 index_copy_ / flash_attn_varlen 接口在参数约定、内存布局期望、对齐要求上完全不同，所以必须适配。

各个硬件后端的适配方式对比

SGLang 目前支持的硬件后端包括：CUDA (NVIDIA)、ROCm (AMD)、Ascend NPU、Intel XPU、MUSA (摩尔线程)、MLX (Apple Silicon)、HPU (Habana Gaudi)、CPU。

它们的适配方式差异巨大，分为 4 种截然不同的策略：

方式一：「全覆盖」型 — Ascend NPU

目录： hardware_backend/npu/ → 15 个文件
策略： 在每一层都提供独立实现，通过 is_npu() 条件导入替换

覆盖范围： 几乎所有计算链路都替换了
优点： 极致适配，可以针对硬件特性做深度优化（FRACTAL_NZ 格式对齐、MOE 双 stream 并发等）
代价： 代码量大（~5000 行），需要随上游 sglang 每个注意力接口变更而更新

方式二：「继承重写」型 — MUSA (摩尔线程)

目录： hardware_backend/musa/attention/ → 1 个文件
策略： 继承 CUDA 的 FlashAttentionBackend，只重写差异部分

class MusaFlashAttentionBackend(FlashAttentionBackend):
    def __init__(self, model_runner):
        super().__init__(model_runner)
        # 只新增了 MUSA 特定的 scheduler metadata 管理

做了哪些：

  • 继承了 FlashAttentionBackend 的全部 forward 逻辑
  • 在 forward_extend() 和 forward_decode() 调用 MUSA 版的 flash_attn_with_kvcache（来自 flash_attn 库的 MATE 版）
  • 额外注入了 scheduler_metadata 计算（MUSA 的 flash attention 需要这个参数）
  • 没有独立的 KV Cache pool / allocator / 量化方法

覆盖范围： 只覆盖 AttentionBackend
优点： 极轻量（~900 行），由于 flash_attn 库已经支持 MUSA，模型层零修改
代价： 只适配了 attention，其他全部走 CUDA 路径（靠 torch.cuda.is_available() 为 True 来混用）

方式三：「零代码」型 — ROCm (AMD) 和 Intel XPU

ROCm（AMD 显卡）：

  • 没有 hardware_backend/rocm/ 目录
  • 策略：通过 torch.version.hip 检测 + 条件替换 1-2 个算子
# 在 deepseek_common/attention_backend_handler.py:26
if is_hip():
    if attn.rocm_fused_decode_mla and forward_batch.forward_mode.is_decode():
        return AttnForwardMethod.MLA_FUSED_ROPE_ROCM
    else:
        return AttnForwardMethod.MLA

做的改动：

  • deepseek_v2.py:171 — ROCm 走 flashinfer 或 triton 的 attention backend
  • forward_mla_fused_rope_rocm.py — 替换 RoPE 融合的前向方法
  • 没有重写 KV Cache / Allocator / Graph

Intel XPU：

  • 没有 hardware_backend/xpu/ 目录
  • 策略：实现一个 XPUAttentionBackend（继承 AttentionBackend，但只有 ~300 行），使用 sgl_kernel 中的 flash_attn_varlen_func 和 flash_attn_with_kvcache

做的改动：

  • attention_registry.py:259 — 注册 "intel_xpu" → XPUAttentionBackend
  • xpu_backend.py — 一个比较简短的 attention backend
  • 没有独立的内存管理 / Graph / 量化

关键原因： AMD ROCm 和 Intel XPU 的 PyTorch 实现都把 torch.cuda 接口完全重映射成自己的，所以绝大多数 CUDA 代码直接跑通。

方式四：「完全替换」型 — MLX (Apple Silicon)

目录： hardware_backend/mlx/ → 6 个文件
策略： 另起炉灶，不依赖 PyTorch，而是直接使用 Apple 的 MLX 框架

# mlx/model_runner.py
import mlx.core as mx
from mlx_lm import load as mlx_lm_load

class MlxModelRunner:
    def __init__(self, model_path, ...):
        self.model = mlx_lm_load(model_path)  # 直接加载模型
        patch_model_attention(self.model)      # 替换注意力层

MLX 是唯一不跑在 PyTorch 上的后端，它有自己的 KV cache 池（MlxKVPool）、自己的 attention wrapper（MLXAttentionWrapper）、自己的 model runner。调度器还是 sglang 的，但执行完全在 MLX 上。

覆盖范围： Model Runner + KV Cache + Attention
优点： 充分利用 Metal GPU 统一内存
代价： 完全独立于 PyTorch 生态，不支持 DeepSeek MLA 等复杂模型

方式五：「无感兼容」型 — HPU (Habana Gaudi)

HPU 没有 hardware_backend/hpu/ 目录，搜索 is_hpu 也几乎没有命中。这是因为 Habana 的 PyTorch 插件（torch.hpu）将 CUDA 接口完全替换，HPU 设备上的 torch.cuda 调用被透明地重定向到 HPU。所以基本上开箱即用。

哪种方式更简单高效？

从简单角度排序：

  1. ROCm / HPU — 最简单。利用 torch.cuda 兼容层，基本零改动
  2. XPU — 次简单。只写一个轻量 AttentionBackend
  3. MUSA — 中等。继承 FlashAttentionBackend 重写关键方法
  4. MLX — 较复杂。需要独立框架 runner
  5. NPU — 最复杂。几乎需要全面覆盖每个子系统

从高效（工程性价比）角度排序：

  1. XPU — 300 行覆盖主流模型推理
  2. MUSA — 900 行覆盖 attention + 投机解码
  3. ROCm — 100 行针对性算子替换
  4. MLX — 适合 Apple 生态，但功能受限
  5. NPU — 适配成本最高，但硬件特性利用最充分

为什么 NPU 选了最重的方式？

根本原因在于 Ascend 的 CANN 算子接口与 CUDA 没有任何兼容性：

接口CUDANPU (CANN)
Attention 算子flash_attn_varlen_functorch_npu._npu_flash_attention_qlens
Paged Attentionflash_attn_with_kvcachetorch_npu._npu_paged_attention
KV 写入index_copy_npu_scatter_nd_update_
模型加载torch.load + CUDAtorch.load + npu_format_cast 转 format
格式约束无FRACTAL_NZ (dim % 16 == 0)

而 ROCm 和 XPU 可以直接用 flash_attn、flashinfer 等库，因为这些库本身就支持 AMD/Intel 硬件。MUSA 也有 flash_attn 的移植版。

结论： 如果你从零开始为一个新的硬件适配推理框架：

  • 如果 PyTorch 已经有该硬件的 backend（能跑 torch.randn(3).to("xpu")）→ 选 XPU 方式（写一个 AttentionBackend，复用其余）
  • 如果 flash_attn 库支持该硬件 → 选 MUSA 方式（继承 FlashAttentionBackend）
  • 如果 PyTorch CUDA 兼容层能工作（torch.cuda 被重映射）→ 选 ROCm 方式（只替换不兼容的算子）
  • 如果 完全不兼容 CUDA（如 Ascend 的 CANN）→ 只能选 NPU 方式（全覆盖适配）
  • 如果 不用 PyTorch（如 Apple MLX）→ 选 MLX 方式（另起炉灶）
